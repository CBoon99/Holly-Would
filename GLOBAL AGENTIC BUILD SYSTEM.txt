GLOBAL AGENTIC BUILD SYSTEM
Canonical Software Delivery, Model-Routing and Governance Standard
Status: Canonical
Version: 1.1
Purpose: Reusable operating system for planning, building, testing, reviewing and safely releasing software with AI agents and human oversight
Applies to: New products, client systems, internal tools, substantial features, integrations, migrations, infrastructure changes and major refactors
Standard owner: Human project owner or designated technical authority
Change authority: Human project owner or explicitly delegated governance owner
Effective date: Record when adopted by each project
Supersedes: Any earlier informal agent-building workflow unless explicitly retained
Independence: This is a global software-delivery standard. It is not tied to BoonMind X, Claude Code, Codex, Cursor, a particular model provider or any single orchestration system.
________________


1. Purpose
This standard governs how autonomous and semi-autonomous AI agents participate in software development.
Its purpose is not to maximise agent activity or generate the largest possible amount of code.
Its purpose is to produce software that is:
* Understandable
* Correct
* Testable
* Secure
* Evidence-backed
* Maintainable
* Traceable
* Reversible or recoverable where practical
* Safe to release
* Consistent with the project’s architecture
* Consistent with the project’s documentation
* Appropriate for the real user and operating environment
The system deliberately separates:
* Understanding
* Risk classification
* Context retrieval
* Discovery
* Planning
* Challenge
* Security and privacy review
* Sandbox preparation
* Building
* Technical verification
* Independent product testing
* Documentation reconciliation
* Evidence assembly
* Acceptance
* Release
* Post-release observation
* Learning capture
No agent may treat implementation as equivalent to completion.
No stage is considered complete merely because an agent reports that it is complete.
Completion requires evidence.
The role or context that builds a feature must not be the only authority that tests, accepts or releases it.
________________

    ↓

3. Core principles
3.1 Evidence outranks confidence
An agent’s confidence, explanation or apparent technical fluency is not proof.
Claims must be supported by evidence appropriate to the claim.
Examples:
* Code behaviour requires test or execution evidence.
* Permission claims require allowed and forbidden access tests.
* Migration safety requires migration and recovery evidence.
* UI claims require rendered or executed product evidence.
* Integration claims require contract, fixture, sandbox or controlled-live evidence.
* Deployment claims require production-safe smoke-test evidence.
* Performance claims require measurements.
* Security claims require inspection and adversarial testing.
* Accessibility claims require automated and, where material, manual checks.
The absence of an observed failure is not proof of correctness.
“Probably fine” is not evidence.
________________


3.2 Separate proposal, implementation, inspection, acceptance and release
Agents may:
* Propose
* Research
* Discover
* Plan
* Challenge
* Build
* Inspect
* Test
* Review
* Recommend
A separate authority accepts and releases the work.
For high-impact production actions, that authority must include a human.
________________


3.3 Use risk-proportionate process
Not every change requires the complete workflow.
Workflow depth must be selected according to:
* Security impact
* Privacy impact
* Financial impact
* Data sensitivity
* Reversibility
* Recoverability
* Architectural impact
* Number of users affected
* Production exposure
* External integration risk
* Regulatory or compliance impact
* Business criticality
* Potential for data loss
* Potential for service interruption
* Potential for reputational harm
Small, safe changes should not be buried in unnecessary ceremony.
High-risk changes must not be rushed through a lightweight path.
________________


3.4 Keep work bounded
Every mission and phase must have explicit boundaries.
Agents must know:
* What is in scope
* What is out of scope
* What “done” means
* What evidence is required
* Which files or components they own
* Which contracts are shared
* What they are not authorised to change
* What conditions require stopping
* What conditions require escalation
No agent may silently expand scope.
________________


3.5 Make invalid states difficult or impossible
Good architecture should prevent invalid states rather than relying only on later detection.
Examples:
* Tenant isolation enforced structurally
* Capability restrictions represented in contracts
* Invalid theme combinations prevented through derivation
* Destructive actions protected by explicit authority
* Unsupported integration behaviour impossible to invoke
* Sensitive data inaccessible to unnecessary model contexts
* Impossible state transitions rejected by the domain model
* Invalid configuration blocked before deployment
________________


3.6 Make confusing states difficult or impossible
Good UX should prevent user confusion rather than merely provide better error messages afterward.
Examples:
* Honest progress indicators
* Visible data recency
* Clear degraded-state behaviour
* Actionable errors
* No silent fallbacks where stale data may cause harm
* No dead ends
* No interface element remaining after its purpose is complete
* Clear distinction between unsupported, unavailable and failed
* Clear recovery paths
* No user blame for system limitations
________________


3.7 External complexity terminates at the boundary
External APIs, vendors, tools and data sources should be normalised at explicit boundaries.
The project core should depend on stable internal contracts rather than external quirks.
This applies to:
* PMS platforms
* Payment providers
* Storage providers
* Authentication systems
* AI models
* Messaging platforms
* Shipping providers
* Commerce systems
* Government APIs
* Analytics services
* File-processing systems
* Search providers
* Scheduling platforms
* Hosting and deployment providers
________________


3.8 Deterministic logic before probabilistic logic
AI should not replace deterministic business logic where correctness can be expressed and tested directly.
Use deterministic code for:
* Financial calculations
* Permissions
* Compliance rules
* Validation
* Data transformations
* State transitions
* Booking ownership
* Security boundaries
* Destructive-action safeguards
* Final database mutations where correctness is critical
* Tenant isolation
* Authentication enforcement
* Contract validation
* Migration ordering
AI may assist with:
* Interpretation
* Classification
* Summarisation
* Drafting
* Routing
* Recommendations
* Natural-language interaction
* Exploratory analysis
* Code-generation proposals
* Test-case generation
* Documentation synthesis
AI output must not silently override deterministic controls.
________________


3.9 Insufficient evidence does not pass
A gate may pass only on sufficient evidence.
When evidence is:
* Incomplete
* Contradictory
* Ambiguous
* Missing
* Unavailable
* Derived only from an agent’s assertion
the default outcome is:
* MORE EVIDENCE REQUIRED, or
* FAIL
No gate may pass on “probably fine.”
________________


3.10 Recovery is a first-class concern
Every material release must define how the system will recover if the change fails.
Recovery may involve:
* Rollback
* Redeploying a previous version
* Database restore
* Forward repair
* Feature disablement
* Traffic isolation
* Connector disablement
* Queue replay
* Read-only mode
* Manual operational fallback
Where rollback is technically safe and appropriate, it should be tested in a sandbox or staging environment.
Where rollback is unsafe or impractical, the phase must define a forward-recovery, containment or restore strategy.
________________


3.11 Traceability exists for accountability, not punishment
Every material output must record who or what produced it.
This includes:
* Producing role
* Agent or human identity
* Model where relevant
* Mission and phase
* Relevant timestamp or sequence
* Context supplied
* Source evidence
* Tools used
This exists for:
* Provenance
* Reproducibility
* Debugging
* Auditability
* Accountability
* Learning
It does not exist to create a blame culture.
________________


3.12 Model diversity is allowed; governance remains constant
The build system may route different tasks to different models or providers where this improves:
* Quality
* Accuracy
* Cost
* Speed
* Context capacity
* Privacy
* Coding ability
* Research ability
* Visual reasoning
* Testing independence
* Tool access
Changing models does not change:
* Acceptance criteria
* Security rules
* Evidence requirements
* Human approval requirements
* Source-of-truth hierarchy
* Scope boundaries
* Required gates
A cheaper or faster model may perform a task only when it is capable of meeting the same required standard.
________________


4. Workflow versioning and change control
4.1 Version recording
Every substantial project should record:
* The workflow version it follows
* The date it adopted that version
* Any approved project-specific deviations
* The authority that approved those deviations
* The project profile mapping the global standard to local files and commands
Every mission should record its governing workflow version.
________________


4.2 Standard changes
Changes to this governing workflow should be:
* Proposed explicitly
* Reviewed independently
* Recorded in a changelog
* Versioned
* Approved by the human owner or delegated authority
Agents must not silently edit the rules governing their own current mission.
A workflow change normally takes effect on the next mission.
It may take effect immediately only when:
* The change closes an active safety or security gap, and
* A human authority explicitly approves immediate application
________________


4.3 No self-weakening
An agent may not change the workflow to:
* Remove a failing gate
* Reduce required evidence
* Avoid independent testing
* Skip security review
* Permit an action it was previously forbidden to perform
* Redefine acceptance criteria after implementation
* Reclassify a high-risk task as low-risk without evidence and approval
* Remove the need for human approval
* Convert a failed test into a warning merely to proceed
________________


5. Human authority and approval
5.1 Conductor identity
The Conductor is a logical role.
It may be:
* A human
* An AI agent
* An AI agent supervised by a human
* A combined human-and-agent operating process
The identity of the Conductor must be recorded for each mission.
________________


5.2 Conductor approval versus human approval
An AI Conductor may:
* Determine that evidence appears to satisfy a phase
* Recommend PASS
* Recommend PASS WITH RECORDED RISK
* Request additional evidence
* Recommend FAIL
* Coordinate remediation
An AI Conductor may not independently authorise:
* A Level 3 production release
* A destructive production action
* A financial commitment
* A legal or contractual commitment
* Acceptance of a critical security risk
* A workflow exception
* Permanent deletion of production data
* A high-impact customer-facing action
For Level 3 changes, human approval is mandatory in addition to Conductor approval.

6. Agent and human roles
These are logical responsibilities.
They may be fulfilled through:
* Separate models
* Separate providers
* Separate agents
* Separate sessions
* Separate context windows
* Separate repository worktrees
* Deliberately isolated passes by the same underlying model
* Human reviewers
* Hybrid human-and-agent processes
The goal is meaningful separation of context, capability and responsibility.
________________


6.1 Conductor
The Conductor owns the mission.
Responsibilities
* Understand the request and intended outcome
* Identify the correct project and repository
* Read the necessary canonical documentation
* Confirm the workflow version
* Classify risk
* Identify dependencies, ambiguity and constraints
* Select the correct workflow depth
* Select suitable agents or models
* Divide work into bounded phases or task packets
* Assign ownership
* Maintain the canonical mission record
* Stop uncontrolled scope expansion
* Review evidence
* Resolve conflicts
* Decide whether a phase passes its gates
* Default to MORE EVIDENCE REQUIRED or FAIL when evidence is insufficient
* Escalate decisions requiring human authority
* Ensure documentation is reconciled
* Assemble the final evidence packet
* Ensure accepted risks have owners
* Ensure release authority is clear
The Conductor coordinates work but should not automatically perform every specialist task.
The Conductor must not accept a phase solely because the Builder says it is finished.
________________


6.2 Discovery Agent
The Discovery Agent establishes the relevant current state before planning.
Responsibilities
* Inspect repository structure
* Find relevant architecture and requirements
* Identify the existing implementation
* Locate relevant tests
* Inspect data models and API contracts
* Identify permissions and trust boundaries
* Determine deployment and environment constraints
* Find existing patterns that should be reused
* Identify active technical debt relevant to the mission
* Distinguish current canonical material from historical material
* Report unknowns and assumptions
* Identify likely file and component ownership
* Identify parallel-work conflicts
* Identify external capability assumptions
Discovery must be targeted.
It must not become unlimited exploration of the entire repository or documentation history.
________________


6.3 Architect / Planner
The Architect converts the required outcome into a buildable plan.
Responsibilities
* Inspect the existing architecture
* Identify affected components, services and data
* Define interfaces and boundaries
* Define source-of-truth ownership
* Identify security, tenancy and permission implications
* Identify privacy and retention implications
* Identify migrations and compatibility risks
* Specify failure and degraded-state behaviour
* Define recovery requirements
* Define testing requirements
* Define migration and rollback or forward-recovery requirements
* Define documentation changes
* Define success criteria
* Define dependencies
* Define component ownership
* Define integration order
* Produce bounded implementation phases
The Architect must explain why the proposed approach fits the project.
A file list without architectural reasoning is not an adequate plan.
________________


6.4 Challenger / Plan Reviewer
The Challenger independently reviews the proposed plan before implementation.
Responsibilities
* Check whether the correct problem is being solved
* Identify hidden assumptions
* Identify missing requirements
* Check for unnecessary scope or complexity
* Check whether existing capability is being duplicated
* Check alignment with the current architecture
* Check interface boundaries
* Examine failure modes
* Examine external dependency failure
* Check security and privacy risks
* Check multi-tenant implications
* Check migration and recovery safety
* Challenge unsupported vendor assumptions
* Challenge whether AI is being used where deterministic logic is safer
* Check whether tests can prove acceptance criteria
* Check whether the proposed phase is too large
* Identify accidental platform expansion
* Identify irreversible decisions
* Identify confirmation bias
* Identify automation bias
* Challenge AI-generated recommendations
* Check whether assumed users, devices, languages or operating conditions are representative
* Check whether model selection is appropriate
The Challenger does not take over the project or rewrite the entire design.
It produces specific, actionable objections and recommendations.
Challenge classifications
* Blocker — must be resolved before build
* Major — should normally be resolved before build
* Minor — may be accepted and recorded
* Observation — informational
All material objections require a documented response.
________________


6.5 Security / Privacy Design Reviewer
This role operates before implementation when triggered.
Trigger conditions
Required when a phase touches:
* Authentication
* Authorisation
* Permissions
* Personal data
* Health data
* Financial data
* Payments
* Passport or identity information
* Multi-tenancy
* File uploads
* External integrations
* Production infrastructure
* AI tool access
* Compliance systems
* Secrets
* Destructive operations
* Data export
* Data retention or deletion
* User impersonation
* Remote command execution
* Model routing involving sensitive data
* New external AI provider use
Responsibilities
* Review trust boundaries
* Review least-privilege design
* Review tenant isolation
* Review secrets handling
* Review sensitive logging
* Review encryption requirements
* Review retention and deletion
* Review consent and lawful-processing assumptions
* Review auditability
* Review abuse controls
* Review rate limiting
* Review destructive-action safeguards
* Review incident-response implications
* Ensure unnecessary sensitive data is excluded from AI contexts
* Review which model providers may receive which data
* Check data-residency or contractual constraints where applicable
The design review should happen before code is written where the risk is architectural.
________________


6.6 Builder
The Builder implements one approved, bounded phase.
Responsibilities
* Follow the approved phase plan
* Respect canonical architecture
* Respect project-specific operating rules
* Work only within authorised scope
* Respect file and component ownership
* Avoid unrelated refactors
* Add or update tests
* Run focused checks during implementation
* Record deviations from the plan
* Stop when encountering a material architectural conflict
* Trigger the doom-loop breaker when required
* Remove debugging code and temporary workarounds
* Remove newly created dead code
* Update affected documentation
* Produce implementation evidence
* Produce a structured build report
The Builder may declare implementation complete.
The Builder may not declare the mission accepted or released.
Prohibited Builder behaviour
The Builder must not:
* Silently reduce acceptance criteria
* Comment out failing tests
* Skip tests without recording why
* Add suppressions merely to pass checks
* Replace real behaviour with stubs while claiming completion
* Make broad unrelated refactors
* Weaken permissions to make tests pass
* Hide failures in empty catch blocks
* Hard-code secrets
* Log sensitive data
* Use unsupported external endpoints without approval
* Call repeated failures environmental without evidence
* Claim completion without running required verification
* Self-approve unresolved failures
* Silently change the governing plan
* Modify files owned by another concurrent Builder without coordination
* Create overlapping migrations without approval
* Commit unrelated generated files or artefacts
* Leave knowingly obsolete branches or duplicate implementations without recording them
________________


6.7 Verification Agent
The Verification Agent checks whether the implementation technically satisfies the approved plan.
Responsibilities
* Inspect the actual diff
* Compare the diff with the phase brief
* Run formatting checks
* Run linting
* Run static analysis
* Run type checks
* Run unit and integration tests
* Run build or compilation checks
* Run database and migration checks
* Inspect recovery readiness
* Inspect security and permission boundaries
* Inspect test quality
* Inspect error handling
* Inspect logging
* Inspect sensitive-data exposure
* Inspect configuration changes
* Inspect dependency changes
* Verify documentation updates
* Check for hard-coded values
* Check for bypasses and temporary stubs
* Confirm no unrelated files changed
* Identify dead code
* Identify unused dependencies
* Identify duplicated logic
* Identify unrelated technical debt
* Produce a structured verification report
The Verification Agent should begin from the assumption that defects may exist.
It should not be instructed to “confirm that the build works.”
________________


6.8 Independent Product Test Agent
The Independent Product Test Agent behaves as an unfamiliar, sceptical or adversarial user.
It tests the product, not the Builder’s intentions.
Context isolation
The Independent Test Agent should receive:
* The original requirement
* The approved acceptance criteria
* Access to a clean sandbox
* Minimal operational instructions
It should not first receive a persuasive Builder summary.
Responsibilities
* Execute expected user journeys
* Test unexpected inputs
* Test failure branches
* Test role and permission separation
* Test direct URL and API access
* Test cross-tenant access
* Test offline and degraded states where relevant
* Test timeouts and retries
* Test browser refresh and interrupted sessions
* Test duplicate actions
* Test concurrency where relevant
* Test realistic devices and screen sizes
* Test accessibility
* Test data creation and updates
* Test audit behaviour
* Test sensitive-data handling
* Attempt to break assumptions
* Look for confirmation and automation bias
* Test unrepresentative user assumptions
* Record reproducible defects
* Distinguish observed, tested, inferred and unverified claims
________________


6.9 Security / Privacy Implementation Reviewer
This role reviews the completed implementation when triggered.
Responsibilities
* Verify design controls were implemented
* Test allowed and forbidden actions
* Test tenant isolation
* Test least privilege
* Inspect logs
* Inspect secret storage
* Inspect error exposure
* Inspect data minimisation
* Test rate limits and abuse controls where appropriate
* Verify destructive safeguards
* Verify data retention and deletion behaviour
* Verify sensitive data is not exposed to AI contexts
* Verify model-routing rules were followed
* Verify external connectors cannot exceed declared capabilities
* Confirm audit records are sufficient
This role is distinct from the pre-build design review.
________________


6.10 Release Reviewer
The Release Reviewer determines whether accepted work is safe to merge or deploy.
Responsibilities
* Confirm all required gates passed
* Review unresolved risks
* Confirm accepted-risk ownership
* Confirm recovery plan
* Confirm migrations
* Confirm environment configuration
* Confirm secrets and access
* Confirm monitoring and logs
* Confirm release notes
* Confirm production smoke-test plan
* Confirm correct branch and commit
* Confirm concurrency integration has completed
* Confirm combined-build verification
* Decide:
   * PASS
   * PASS WITH RECORDED RISK
   * MORE EVIDENCE REQUIRED
   * FAIL
________________


6.11 Human Owner
The human owner retains final authority over:
* High-risk production releases
* Destructive production actions
* Financial actions
* External communications
* Legal or contractual commitments
* Changes involving sensitive customer data
* Accepted major risks
* Workflow governance changes
* Workflow exceptions
* Emergency exceptions
* Product-direction decisions
* Provider contracts
* Model-provider approval for sensitive data
* Permanent production-data deletion
Agents support judgment.
They do not replace accountable ownership.
________________


7. Model routing and multi-model execution
7.1 Purpose
The system may use different models for different tasks.
This can improve:
* Output quality
* Cost efficiency
* Speed
* Specialist capability
* Context handling
* Privacy
* Testing independence
* Tool compatibility
* Resilience against one-model failure
The objective is not to use as many models as possible.
The objective is to use the lowest-cost, lowest-risk model that can reliably meet the task’s quality requirement.
________________


7.2 Model-selection criteria
The Conductor should consider:
* Task complexity
* Required reasoning depth
* Required coding ability
* Required context length
* Need for visual reasoning
* Need for web research
* Need for tool use
* Need for structured output
* Latency
* Cost
* Privacy
* Data sensitivity
* Provider terms
* Reliability
* Independence from the Builder
* Known model weaknesses
* Availability
________________


7.3 Suggested model lanes
High-reasoning lane
Appropriate for:
* Architecture
* Complex planning
* Security design
* Difficult debugging
* Cross-system reasoning
* High-risk code review
* Migration planning
* Root-cause analysis
Fast implementation lane
Appropriate for:
* Bounded code changes
* Boilerplate
* Straightforward tests
* Repetitive refactors
* Documentation updates
* Small bug fixes
Research lane
Appropriate for:
* External API documentation
* Vendor capability verification
* Standards
* Current framework behaviour
* Legal or regulatory source collection
* Market or product research
Independent review lane
Appropriate for:
* Plan challenge
* Diff review
* Adversarial testing
* Security review
* Requirements-first product testing
Where practical, this should use a different model, provider or isolated context from the Builder.
Local/private lane
Appropriate for:
* Sensitive context routing
* Local summarisation
* Evidence triage
* Redaction assistance
* Offline tasks
* Lightweight classification
* Private policy checks
Visual lane
Appropriate for:
* UI inspection
* Screenshot comparison
* Responsive-layout checks
* Design-system review
* Accessibility inspection
* Diagram interpretation
________________


7.4 Routing rules
The Conductor may switch models between tasks.
The Conductor should record:
* Model selected
* Task assigned
* Reason for selection
* Data supplied
* Cost or capability rationale where relevant
* Whether the model is allowed to use external tools
* Whether sensitive data was excluded
* Whether output requires independent verification
________________


7.5 Value optimisation
Model routing should optimise overall value, not merely per-token cost.
A cheaper model is not better value if it:
* Introduces defects
* Requires repeated corrections
* Causes doom loops
* Misses security implications
* Produces poor tests
* Expands scope
* Requires expensive rework
A stronger model may be better value for:
* Architecture
* Planning
* Difficult debugging
* Security
* Root-cause analysis
A faster or cheaper model may be better value for:
* Repetitive implementation
* Formatting
* Mechanical refactoring
* Basic documentation
* Fixture generation
________________


7.6 Escalation between models
A task should move to a more capable model when:
* The same failure repeats twice
* Diagnosis confidence remains low
* The task crosses several architectural boundaries
* The current model cannot hold the required context
* The model repeatedly violates constraints
* Security implications emerge
* The implementation becomes materially different from the approved plan
* Tests reveal a systemic issue
* External evidence is contradictory
A task may move to a cheaper or faster model when:
* The plan is stable
* The task is bounded
* Acceptance criteria are explicit
* Relevant contracts are supplied
* The work is mechanically verifiable
* A stronger model is not needed for safe completion
________________


7.7 Model independence
Independent verification should not simply ask the Builder model:
“Are you sure?”
Preferred independence order:
1. Different model provider
2. Different model family
3. Different model instance with isolated context
4. Fresh session with requirement-first prompting
5. Human review
High-risk work should use stronger independence where practical.
________________


7.8 Sensitive-data routing
Sensitive data must not be sent to a model merely because that model is technically available.
Before routing sensitive context, confirm:
* Provider approval
* Data-processing terms
* Project privacy policy
* Tenant permission
* Data minimisation
* Redaction
* Retention behaviour
* Region or residency requirements
* Whether a local/private model is more appropriate
________________


7.9 Model fallback
If the preferred model is unavailable:
* Do not silently downgrade high-risk work.
* Reclassify the available capability.
* Decide whether the task can safely proceed.
* Record the fallback.
* Require additional verification where appropriate.
* Pause the task if no available model can meet the required standard.
________________


8. Source-of-truth hierarchy
When instructions conflict, agents must use this hierarchy:
1. Current explicit human instruction
2. Current approved mission or phase brief
3. Canonical architecture and system-design documents
4. Security, privacy, evidence and governance rules
5. Approved product requirements
6. Explicit API, schema and behavioural contracts
7. Current tests that represent approved behaviour
8. Current implementation
9. Current working-state documents
10. Historical notes, archived plans and old build logs
11. Agent assumptions
Existing code is not automatically correct merely because it exists.
Documentation is not automatically correct if it has been superseded.
Tests are not automatically authoritative if they encode obsolete behaviour.
Any material conflict must be surfaced rather than silently resolved.
________________


9. Context and token management
9.1 Principle
Agents should load the minimum context required to perform the current task correctly.
More context is not automatically better.
Uncontrolled context loading can:
* Waste tokens
* Increase cost
* Reduce attention on the active requirement
* Reintroduce obsolete decisions
* Blend conflicting plans
* Encourage unnecessary refactors
* Increase hallucinated relationships
* Expose sensitive information unnecessarily
* Slow execution
* Make independent review less independent
Do not load all project documentation by default.
________________


9.2 Context preference hierarchy
Agents should normally load context in this order:
1. Active mission or phase brief
2. Current working-state or next-action summary
3. Governing workflow rules required for the current phase
4. Relevant architecture or domain contract
5. Exact source files and tests being changed
6. Relevant security or evidence rules
7. Relevant external API contracts
8. Evidence documents only when evidence is explicitly needed
9. Historical documents only when:
   * The task asks for history
   * Current documents are ambiguous
   * A decision’s origin materially affects the work
   * A regression requires historical comparison
________________


9.3 Context retrieval triggers
Projects may maintain modular context documents or context pots.
Agents retrieve them only when triggered by the task.
Task
	Required context
	Worker or tool execution
	Agent workflow, task-packet contract, orchestration rules
	Upload or evidence handling

10. Doom-loop prevention
10.1 Definition
A doom loop occurs when an agent repeatedly applies local changes without improving its understanding of the failure.
Typical signs:
* The same check fails repeatedly
* Different speculative fixes are attempted without diagnosis
* Tests are weakened
* Suppressions accumulate
* Errors are blamed on the environment without evidence
* The agent alternates between two broken states
* Scope grows as a substitute for understanding
* The same file is repeatedly rewritten
* The same context is reread without new evidence
* Models are switched repeatedly without a clear reason
________________


10.2 Mandatory loop breaker
If the same check fails twice with materially equivalent symptoms after attempted correction:
Stop. Do not make another speculative change.
Produce a loop-stop report containing:
* Failed check
* Exact observed symptom
* What changed in each attempt
* Suspected cause
* Evidence supporting the diagnosis
* Evidence contradicting the diagnosis
* Confidence in the diagnosis
* Whether the original plan or assumption may be wrong
* Whether the model may be unsuitable for the task
* Next safe action
* Whether a stronger model is required
* Whether replanning or escalation is required
________________


10.3 Prohibited loop responses
Agents must not respond to repeated failure by:
* Weakening tests
* Skipping tests
* Adding broad ignores
* Adding type suppressions without justification
* Disabling lint rules
* Removing assertions
* Calling the failure environmental without evidence
* Replacing the real dependency with a permanent mock
* Increasing timeouts blindly
* Reinstalling repeatedly without diagnosis
* Editing unrelated systems
* Switching models randomly
* Claiming partial success as completion
________________


10.4 Learning capture
When a doom loop reveals a reusable lesson, create a Learning Candidate.
A Learning Candidate records:
* Problem pattern
* Root cause
* Misleading initial assumption
* Evidence
* Corrective action
* Where the rule should live
* Whether it should become:
   * Documentation
   * Test
   * Lint rule
   * Static check
   * Template change
   * Architecture principle
   * Agent instruction
   * Runbook step
   * Model-routing rule
A correction that should persist must not remain only in an agent conversation.
________________


11. Tool and action authority
11.1 Action classes
Class A — Read-only
Examples:
* Read files
* Inspect repository
* Read logs
* Search documentation
* Query non-sensitive test data
Normally permitted within scope.
Class B — Local reversible write
Examples:
* Edit sandbox files
* Create tests
* Modify a feature branch
* Change disposable local data
Permitted to the Builder within an approved phase.
Class C — Remote reversible write
Examples:
* Push a branch
* Create a draft pull request
* Update a preview environment
* Create a draft email
* Create a non-production test resource

Class D — Production or customer-facing write
Examples:
* Deploy production
* Modify production configuration
* Update customer data
* Send external communication
* Publish content
* Change a live integration

* Drop tables
* Rotate production credentials
* Disable authentication
* Change billing
* Send payments
* Permanently delete files
* Modify legal or compliance submissions
* Change live DNS

Requires explicit human approval immediately before execution unless an approved emergency runbook states otherwise.

Do not give development agents unrestricted production access by default.
Do not expose:

* Customer credentials
* Full personal datasets
* Passport images
* Payment information
* Private keys
* Unredacted logs
unless required, approved and appropriately controlled.

* Publish announcements
* Make legal commitments
* Accept vendor terms
* Negotiate contracts
* Purchase services
* Change billing

CAPTURE EVIDENCE
    ↓
DIAGNOSE
    ↓

    ↓
REVISE PLAN OR MODEL ROUTING IF NECESSARY

* Evidence
* Compensating control
* Residual risk
* Human approver
* Expiry or follow-up
* Whether the exception may recur

* Tenant-isolation failures

22. Minimum test layers
Each phase must deliberately choose appropriate test layers.
Unit tests
Prove isolated deterministic logic.
Integration tests
Prove components, databases and services work together.
Contract tests
Prove connectors and APIs respect agreed interfaces.
Permission tests
Prove allowed and forbidden behaviour.
Tenant-isolation tests
Prove one tenant cannot access another tenant’s data or resources.
End-to-end tests
Prove complete user journeys.
Property tests
Prove invariants across generated inputs.
Examples:
* Theme contrast
* Parsers
* Scoring systems
* Data transformations
* Permission invariants
* Tenant-isolation invariants
* Serialization
* Idempotency
Migration tests
Prove schema changes apply safely.
Recovery tests
Prove rollback, restore, containment or forward recovery where relevant.
Manual exploratory tests
Find problems not anticipated by formal test cases.
Adversarial tests
Attempt misuse, malformed inputs and unsafe sequences.
Accessibility tests
Verify keyboard use, contrast, focus, zoom and assistive behaviour.
Performance tests
Verify latency, throughput and resource use where relevant.
Production smoke tests
Confirm deployed behaviour without causing harm.

25. Resource and exploration budgets
Agents must avoid unlimited exploration and repair attempts.
Projects may set explicit numerical budgets.
At minimum:
* Discovery must be targeted.
* The same failure may not receive a third speculative fix.
* Unavailable external services must not be retried indefinitely.
* Repository-wide refactors require explicit approval.
* Historical documents are loaded only when triggered.
* Large dependency changes require justification.
* Test retries require diagnosis when results repeat.
* Model switching must have a reason.
* Agents stop when authority, evidence or access is insufficient.
When a budget is reached, the agent reports:
* What was attempted
* What was learned
* What remains unknown
* What evidence is missing
* Whether a different model is appropriate

26. Emergency production path
A production emergency may require a reduced sequence.
This is an exception, not the default workflow.
Emergency priorities
1. Protect people and data.
2. Contain active harm.
3. Preserve evidence.
4. Restore safe service.
5. Use the smallest reversible intervention.
6. Maintain human authority.
7. Complete retrospective review afterward.
Emergency procedure
* Record incident start
* Identify impact
* Assign human incident owner
* Restrict access
* Capture logs and state
* Apply smallest safe containment
* Avoid unrelated changes
* Verify service restoration
* Monitor
* Record all actions
* Perform retrospective testing
* Reconcile documentation
* Create follow-up missions
* Record root cause
* Create Learning Candidates where relevant
Emergency status does not authorise:
* Unnecessary data deletion
* Concealing changes
* Skipping evidence preservation
* Unrestricted production experimentation
* Permanent architectural shortcuts without follow-up
* Removal of human accountability

35. Definition of done
A phase is done only when:
* Approved scope is implemented
* Acceptance criteria are met
* Appropriate tests exist
* Technical verification passes
* Independent testing passes
* Security/privacy review passes where required
* Documentation matches implementation
* Known limitations are recorded
* Accepted risks have owners
* Technical-debt observations are recorded
* Dependencies are resolved
* Concurrent work is integrated
* Evidence is stored
* Recovery procedure is known
* Release procedure is known
* The authorised Conductor or human owner accepts the phase
* Human approval is recorded where mandatory
These are not equivalent to done:
* Code written
* Builder says complete
* Tests pass only in the Builder’s environment
* Happy path works
* Screenshot looks correct
* A mock works
* Documentation says it should work
* Agent is highly confident
* One model agrees with another
* Production deployment completed without smoke testing
* A recovery plan exists only on paper
* Evidence is incomplete

36. Governing rules
1. Plan before coding.
2. Classify risk before selecting workflow depth.
3. Load minimum required context.
4. Do not load all documentation by default.
5. Challenge material plans before implementation.
6. Keep phases bounded.
7. Declare dependencies before concurrent work.
8. Assign file and component ownership.
9. Build in isolation.
10. Apply least privilege.
11. Never expose secrets or sensitive data unnecessarily.
12. The Builder cannot be the only tester.
13. Requirements drive tests.
14. Test failure paths, not only happy paths.
15. Evidence outranks confidence.
16. Insufficient evidence produces MORE EVIDENCE REQUIRED or FAIL.
17. Distinguish observed, tested, inferred and unverified claims.
18. Documentation changes with behaviour.
19. Recovery is a first-class artefact.
20. External integrations require declared capabilities.
21. External integrations require contract tests.
22. Webhooks provide speed; reconciliation provides truth.
23. Sensitive systems require security review.
24. Production deployment is a separate gate.
25. No agent may silently redefine “done.”
26. No unresolved blocker may be hidden in a summary.
27. Every accepted risk must have an owner.
28. High-impact production actions require human authority.
29. Architecture should make invalid states difficult or impossible.
30. UX should make confusing states difficult or impossible.
31. External complexity terminates at explicit boundaries.
32. Workers receive compact task packets, not full project history.
33. Reviewers receive the diff and relevant contract, not unnecessary context.
34. The same failure twice triggers diagnosis, not a third speculative patch.
35. Do not weaken tests to escape a failure.
36. Reusable corrections must be captured in docs, tests, tooling or Learning Candidates.
37. No agent may weaken the workflow governing its current mission.
38. Emergency work must still preserve evidence and human accountability.
39. Unsupported behaviour must never be implied.
40. Deterministic controls override probabilistic suggestions.
41. Release is complete only after production-safe verification.
42. Real-world behaviour must be compared with planning assumptions.
43. Material discrepancies become explicit new missions.
44. Human accountability remains final.
45. The Conductor may be human, AI or hybrid, but Level 3 release requires human approval.
46. Different models may be used for different tasks.
47. Model routing must optimise total value, not token price alone.
48. Model switches must be recorded and justified.
49. Sensitive data may only be routed to approved models.
50. A model downgrade must not silently reduce quality or safety requirements.
51. Independent review should use a different model or isolated context where practical.
52. Concurrent branches must pass combined integration testing.
53. Unrelated technical debt must be recorded without uncontrolled scope expansion.
54. Traceability exists for provenance and accountability, not punishment.
55. Controlled exceptions require explicit human approval and compensating controls.
56. Critical security, isolation, data-loss and legal-authority failures cannot be overridden.
57. Bias checks apply to plans, AI recommendations, UX assumptions and tests.
58. A material release must have a recovery strategy.
59. Where safe and appropriate, recovery must be rehearsed.
60. “Probably fine” is never a passing result.

37. Final operating principle
Agents may propose, plan, build, inspect and test. Evidence determines whether the work passes. A separate authority accepts and releases it.
The objective is not maximum automation.
The objective is controlled, repeatable leverage.
A good agentic system does not merely produce more code.
It produces software whose:
* Intent is known
* Scope is bounded
* Architecture is respected
* Risks are visible
* Dependencies are controlled
* Models are selected intelligently
* Context is minimised
* Behaviour is tested
* Evidence is retained
* Recovery is possible
* Failures are diagnosed
* Decisions are traceable
* Release is controlled
* Human authority is preserved
* Lessons persist
That is the standard.

# Recovery Classifications


Recovery falls into two categories.


## Planned Recovery


Planned recovery is designed, reviewed and rehearsed before deployment.


Examples include:


- rollback
- redeploy previous release
- database restore
- feature disablement
- traffic isolation
- forward repair


Where technically appropriate, planned recovery should be tested in a sandbox or staging environment.


---


## Emergency Recovery


Emergency recovery occurs when production behaviour is actively causing unacceptable impact.


Emergency recovery:


- prioritises containment
- requires a designated human incident owner
- follows the emergency production procedure
- preserves evidence wherever practical
- records all actions taken


Every emergency recovery must produce:


- incident report
- root cause analysis
- follow-up mission
- Learning Candidate where appropriate

Evidence Confidence
Place immediately after Claim Classification.
# Evidence Confidence


In addition to claim classification, important findings should record confidence.


Recommended confidence levels:


## Critical


Directly observed in production or independently verified through multiple trusted sources.


## High


Strong evidence with successful independent verification.


## Moderate


Supported by testing or inspection but lacking independent confirmation.


## Low


Based primarily on reasoning, inference or limited testing.


## Unknown


Insufficient evidence exists to assess confidence.


Confidence describes the strength of supporting evidence.


Confidence is independent of importance.


A critical production issue may initially have Low confidence until investigation confirms the cause.


Mission dashboards may summarise confidence across major project areas.
